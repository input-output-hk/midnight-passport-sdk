# ADR 0020: Version the Ledger 9 ACC key-generation profile

Status: accepted for bounded source implementation, 2026-11-22. This
decision does not register another supported SDK binding or change the
published package. It follows [ADR 0004](0004-artefact-hashes-committed-compiler-deterministic.md),
[ADR 0008](0008-restore-prover-keys-from-pinned-zkir.md) and the
[Midnames 0.2.0 acceptance map](../../docs-site/architecture/milestone-0.2.0.md).

## Evidence and decision

The frozen `acc-s3r1.1` Compact 0.35 source produces the same 52 ZKIR files
under Compact 0.35 and 0.36. Regenerating their prover and verifier keys with
the 0.36 `zkir-v3` changes 48 pairs. On a fresh Ledger 9 chain, the stable
`9.0.2` prover refused the old JubJub NIGHT withdrawal keys, then completed
that withdrawal and the recipient deposit after a fresh source ACC deployed
with the [entire alternate verifier roster](../../examples/midnames-local/evidence/stable-full-roster-night-send-20261122.json).
This source retained the 0.35 generated module, runtime and ZKIR. It is a
diagnostic profile, not a supported Compact 0.36 compiler/runtime migration.
The [subsequent 0.36.1 inventory](../../examples/midnames-local/evidence/compact0361-acc-key-inventory-20261122.json)
regenerated all 52 pairs with the patch-release key generator; every prover
and verifier hash matched the 0.36.0 inventory. The candidate pins 0.36.1
because [upstream fixed a key-generation defect](https://github.com/midnightntwrk/compact/releases/tag/compactc-v0.36.1)
in that patch release. The
newly packaged key manifest, small ZKIR/verifier bundle, derived artifact
manifest and restore CLI are source candidates. The generated registry now
records a provisional `acc-s3r1.1-zkir036` row with the complete circuit pins.
`resolvePinnedBinding` exposes that row for explicit source host qualification;
`resolveBinding` and `SUPPORTED_BINDINGS` still admit only `acc-s3r1.1`.
The source service may select the provisional row only with a separate verified
asset tree. The demo account admission still refuses it. No new native run or
wider circuit qualification follows from the offline patch comparison.

An on-chain verifier change defines a **new binding identity**. Never replace
key files under `acc-s3r1.1`, reinterpret its existing deployments, or make a
new key profile the default through a local environment variable. Introduce
the candidate ID `acc-s3r1.1-zkir036` as a provisional registry pin until its
complete consumption path is qualified. Keep `acc-s3r1.1` as the default for existing
accounts and the RC compatibility prover profile until the new candidate
passes its own acceptance. A future ACC compile with a 0.36 module/runtime
needs another identity and its own review.

## Admission for the candidate binding

1. Pin the original source revision, Compact 0.35 compiler manifest and
   generated module bytes separately from the 0.36.1 ZKIR key generator and
   recipe. Reproduce all 52 prover/verifier hashes from the exact ZKIR input;
   the [inventory](../../examples/midnames-local/evidence/compact036-acc-key-inventory-20261122.json)
   is the starting comparison, not a release manifest.
2. Add a complete versioned artifact manifest and restoration path. The
   source restore CLI now selects the 0.36.1 generator for the candidate and
   verifies every regenerated key. The source staging CLI assembles an isolated
   full tree and verifies each file against the derived manifest without
   replacing old assets. The source service can select a separate verified
   asset directory for its compiled contract, verifier reads and proof
   providers together. The registry row is provisional; the SDK and browser
   admission guards still refuse it until the complete service and browser
   path is qualified.
   Keep large prover keys outside the npm tarball, but verify their downloaded
   or regenerated bytes against independent hashes before proving.
3. Update `ACC_REGISTRY`, its generator, module loader, service binding pin,
   name-to-ACC reader and demo value routes together. Detect the deployed
   verifier assignment by circuit name; a matching unordered hash set alone
   is insufficient. Refuse unsupported or mixed rosters before an owner
   credential request. The source and recipient may use different supported
   bindings, so the host must check each separately rather than treating one
   network-level binding ID as both accounts' identity.
4. Qualify deployment, activation, NIGHT funding, browser-reviewed withdrawal,
   durable two-leg recovery, indexed recipient deposit, and negative cases on
   the exact signed source and release prover. Keep broader ACC circuits
   unavailable in the new profile until their proof and safety gates pass;
   the full verifier roster alone does not prove every operation works.
5. Retain the old binding and its existing-account compatibility. An
   application must explicitly opt into the new profile for a fresh ACC;
   there is no in-place migration of a maintenance-retired contract. Release
   and real-provider acceptance remain separate.

This preserves the SDK's version axis and avoids claiming that the diagnostic
full-roster payment is already an installable or supported binding.

## Bounded local qualification after this decision

The provisional `acc-s3r1.1-zkir036` route is available only behind explicit
isolated-local host admission. A [fresh native roster refusal](../../examples/midnames-local/evidence/candidate-acc-night-roster-refusal-20261123.json)
deployed an activated ACC whose `deposit_unshielded` verifier differed from
the pin while its other 51 assignments matched. A name pointing to that ACC
was refused before owner approval, signing, journal admission, or a payment
leg. The name was then restored to a valid candidate ACC, and the same run
finalized one synthetic-owner 4 NIGHT payment with original-only recovery.
This qualifies one changed-verifier negative on Ledger 9. Mixed-version
source/recipient pairs, other malformed rosters, source and installed-package
operation coverage, and binding promotion remain separate gates. The ordinary
supported binding and existing deployments are unchanged.
