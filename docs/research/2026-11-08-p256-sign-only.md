# P-256 unshielded withdrawal: scoped ownership without unused PRF

Date: 2026-11-08. **Source preview after published RC7.** This records an implemented
browser-adapter change and its focused software tests. It does not change published
exports, the Lace PRF recipe, login verification or the ACC's strict signing profile.

## Dependency trace and decision

The P-256 unshielded withdrawal in `packages/account/src/connector.ts` captures the
exact asset, base-unit amount and recipient, then invokes the authorizer's
`withKeySession(work, flow)` with that descriptor. Inside the session it checks the
selected public key/credential/policy against the account, reads the live device
counter/auth nonce, computes the binding's challenge, requests a fresh strict P-256
signature and dispatches the value call.

That path does not decrypt a sealed reader, select a private coin or read an encrypted
journal. The previous browser mapping eagerly called `prf.withSession` on session
entry, creating a separate `derive-keys` assertion before the necessary `sign`
assertion. The extra PRF material had no consumer in this operation. PRF assertions
cannot be merged into strict wa-json134 signatures, whose authenticator data excludes
extensions; removing an unused dependency preserves that distinction.

Only the browser P-256 `withdraw-unshielded` key session now enters an internal
ownership scope without loading PRF outputs. The account's generic session hook and
exact descriptor still run, so a host wrapper can refuse before work. The required
transaction signature remains fresh, credential-pinned and user-verified. A host that
explicitly derives a secret within that scope still triggers reviewed PRF access.
Public `prf.withSession` stays eager, as do other key-session flows. Shielded/private
holding and encrypted-journal paths keep their key requirements. A login assertion
never substitutes for a transaction signature.

## Lifetime and selection invariants

The internal `prf-ownership.ts`, `selection.ts` and `pinned-options.ts` helpers keep
the adapter entry points small without adding public exports or a dependency:

- Lazy/eager users own one selected binding. Overlapping key users share a load;
  the final user clears the adapter's owned PRF buffers. Returned secret copies remain
  the caller's responsibility. No timer, persistent cache or owner enrollment is added.
- Selection revisions and owned binding snapshots prevent create/identify/login from
  replacing an active key scope. An in-flight selector also refuses reverse key-scope
  entry. Delayed old `owns` callbacks cannot adopt a later selection. Public binding
  arrays and points are copies, and policy admission rechecks after copying.
- Credential methods retain their captured native receiver through asynchronous
  approval. The actual credential call and signature completion check their captured
  selection/ownership epoch. An abandoned login cannot authorize a late paused access.
- A failed shared load is sticky within its ownership epoch, including synchronous
  failure. Catching a failure cannot silently request PRF again or continue a paused
  signature after that failure. A new explicitly initiated scope can recover once
  the previous owners finish.
- Login retains its separate identification phase, verified sealed-reader checks,
  optional verified handoff and force-disposal on completion/failure. Late identification
  outputs are cleared. Hosts must await their work; an ordinary unawaited child keeps
  ownership until completion, while login has the stronger force-dispose boundary.

Sharing key ownership does not serialize chain mutations or grant another operation
consent. Hosts still enforce account/authentication revisions, live authority, exact
intent, dispatch guards and durable unknown-result fences. A local expiry after
submission cannot erase an acknowledgement or justify replay.

## Consent composition

The reusable library supplies an optional metadata/refusal hook before each actual
credential call. It supplies no operation dialog, blanket approval or automatic fresh
passkey policy for software owners. The reference demo additionally binds immutable
owner unshielded-transfer/export intent to its actual `derive-keys` or `sign` review.
It checks the approved transfer prefix/scheme immediately before its value POST and
rechecks the exported account/grant plus handoff context before sensitive display.
Staging the intent alone grants no approval.

A normal P-256 unshielded owner transfer therefore uses its exact transaction review
and fresh `sign` in one app dialog for that actual call. Known profile retries still
need independently approved assertions, and other critical operations may have
multiple signatures or separate exact administration reviews. A matching bounded
JubJub grant transfer keeps standalone exact consent because it makes no credential
call. No universal one-dialog/one-request claim follows from this change.

## Focused evidence and limits

The new tests use the actual account/WebAuthn ES256/keyring code with the existing
software authenticator and fake chain. The focused local run passed **106 tests**:
25 new tests plus 81 existing creation, strict-profile, login, handoff, session and
unshielded-withdrawal tests. Scoped compilation, strict new-test checkJs, formatting,
default AST budgets and scoped diff checks passed. The raw local receipt lives under
ignored `review/overnight-p256-sign-only-validation/`; this document is not a claim
that every later source revision has the same receipt.

| Exercised case | Observed credential access |
| --- | --- |
| Normal P-256 unshielded withdrawal | One fresh `sign` get; no PRF extension; required UV, pinned ID and exact binding challenge. PRF unavailable after setup does not trigger fallback. |
| Another transaction | Another fresh assertion. |
| One recognized GREASE retry | Two `sign` gets with attempts 1/2; declining retry prevents the second get and dispatch. |
| Host session refusal or sign-review refusal | Zero new gets and zero dispatches. |
| Selected login followed by nested transfer | One `identify-and-unlock`, then one fresh `sign`. |
| Login abandoned while sign review waits | Only login reaches the provider; late sign/dispatch refuses. |
| Explicit nested PRF refusal caught during review | That requested PRF access occurs; the paused sign refuses without retry. |
