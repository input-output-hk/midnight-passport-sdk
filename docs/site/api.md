The public flow is `createPassportAccounts(ports): PassportConnectorAPI` from `mn-passport-account`. The interfaces are in `mn-passport-protocol`; adapter authors import the contracts from `mn-passport-account/ports`. Source links below point to the exact prototype API.

```ts
import { createPassportAccounts } from '@input-output-hk/mn-passport-account';
import type { PassportPorts } from '@input-output-hk/mn-passport-account/ports';

declare const ports: PassportPorts; // supplied by the host adapters
const passport = createPassportAccounts(ports);
const account = await passport.createAccount({
  userName: 'alice',
  retireAuthority: true,
  onEvent: (event) => console.log(event.step, event.phase),
});
const state = await account.state();
```

`retireAuthority` is required. `true` removes the maintenance authority after the last deployment wave and cannot be undone. A host must make that choice explicitly. The account connector supports P-256 WebAuthn and JubJub Schnorr creation and opening. The typed `k256-ecdsa` arm is not implemented.

## Flow methods

| Method                                                            | Result                     | Behaviour                                                                                                                      |
| ----------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `createAccount({ userName, retireAuthority, signal?, onEvent? })` | `PassportAccount`          | Creates a passkey, deploys the ACC, records a directory hint and activates the first device.                                   |
| `openAccount({ signal?, onEvent? }?)`                             | `PassportAccount`          | Finds a registered account with a passkey, verifies ownership against the chain and reopens it.                                |
| `openAccountAt(address, options?)` | `PassportAccount` | P-256 and JubJub: opens a live sealed ACC by address when its credential has no directory hint. Requires a live device entry and an envelope that opens the ledger `enc_key`. JubJub also checks one current matching device registration, then saves its hint and local use counter. |
| `account.state()`                                                 | `PassportAccountState`     | Reads `booted`, `authNonce`, `deviceEpoch`, `entryCount` and `specVersion`. `entryCount` counts entries, not distinct devices. |
| `account.withdrawUnshielded({ color, amount, recipient }, options?)` | `PassportOwnerTransferResult` | P-256 and JubJub owners: signs the pinned `withdraw_unshielded` challenge and submits a transfer from ACC unshielded balance to a Midnight user address. The consent descriptor names the asset color, amount and recipient. Requires the `acc-s3r1.1` binding and an active live owner device. |
| `account.withdrawShielded({ inboxIndex, color, amount, recipient }, options?)` | `PassportOwnerTransferResult` | Sealed P-256 and JubJub owners: selects one chain-matched qualified coin, binds it into the owner challenge and `held_coin` witness, then submits `withdraw_shielded_with_p256` or `withdraw_shielded_with_jubjub`. `recipient` is a 32-byte Zswap coin public key. Requires a `QualifiedHoldingSource`, owner key session, and chain adapter with a per-call witness. |
| `account.rotateEncryptionKey(newKey, options?)`                   | `{ txHash, blockHeight? }` | Legacy P-256 accounts only. Sealed P-256 accounts use `rotateViewingKey` so readers and holdings receive the new secret. |
| `account.rotateViewingKey(options?)`                              | `{ txHash, droppedDeviceEntries, sealedReadGrants, unsealedGrantIds }` | Sealed JubJub and P-256: seal a random secret to unique live devices and chain-confirmed read grantees, rotate the ACC key, then re-encrypt verified holdings. Requires host-backed holding and complete active read-grant sources; reports grants whose key opening or seal is unavailable. |
| `account.removeDevice(commitmentHex, options?)` | `DeviceRemovalResult` | Sealed JubJub and P-256: refuse self-removal or an absent live target, rotate the viewing and roster keys while excluding the target, re-encrypt verified holdings and seal active read grants, then sign the arm's `remove_device` circuit. Requires the same complete host sources as rotation. Returns the rotation and removal transaction hashes. |
| `account.addDevice(reader, options?)` | `DeviceEnrollmentResult` | JubJub and P-256: validates the joining reader, delivers sealed account keys, then enrolls the derived live commitment. A joining P-256 reader needs `scheme: 'p256-webauthn'` and the 32-byte RP hash/21-byte origin policy; a P-256 owner can also enroll a JubJub reader. With active read grants, either owner arm rotates the viewing and roster keys, reseals every active grantee, then delivers only fresh keys to the joiner. The result includes the rotation transaction and grant seals. |
| `account.readShieldedHoldings(options?)`                           | `PassportShieldedHolding[]` | JubJub and sealed P-256: opens coin descriptions inside a `read-holdings` key session and returns those confirmed against chain-owned outputs. Requires the host's `VerifiedHoldingSource`. |
| `account.issueGrant(scope, options?)` | `PassportGrantIssueResult` | JubJub and sealed P-256: confirm the live grant and sealed bookkeeping before returning `active`. A read grant rotates the viewing secret before issue, then publishes a seal to the new grantee; the result includes `rotation` and `sealedReadGrant`. Requires the complete rotation ports, host-pinned origin, live grant source, local records and durable journal. |
| `account.revokeGrant(grantId, options?)` | `PassportGrantRevokeResult` | JubJub and P-256: confirm the inactive ACC tombstone. A read grant rotates the viewing secret first, omits its grantee from new seals, re-encrypts verified holdings, and returns the rotation and surviving reader seals. P-256 requires sealed keys and live grant details; JubJub also requires local records. |
| `account.revokeAllGrants(options?)` | `PassportGrantRevokeAllResult` | JubJub and sealed P-256: clear all grants and tombstones, then confirm the empty ACC map and advanced grant generation. When read grants are live, rotate the viewing secret away from every grantee first and include the rotation result. P-256 legacy accounts still refuse live read grants. |
| `account.recoverPendingGrants(options?)` | `PassportGrantRecoveryResult` | JubJub and sealed P-256: enumerate durable staged openings, publish those active on chain, and report the rest as unsettled without issuing another grant. Requires a journal with `pending(account)` enumeration. |
| `account.grantRoster()` | `PassportGrantRoster` | Reads public grant IDs, active/read flags, generation and nonce from one live ACC grant-map snapshot. |

The account object also exposes `address`, `networkId`, `bindingId`, `scheme` and, for passkeys, `credentialId`. `apiVersion` is currently `1.0.0-pre.0`. See [protocol `api.ts`](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/protocol/src/api.ts) and [account `connector.ts`](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/account/src/connector.ts).

For an unshielded withdrawal, pass lowercase 64-character hex strings for `color` and `recipient`, and a canonical positive decimal `amount` no greater than `2^128 - 1`. The account confirms the selected device is still live, binds those exact fields and the current ACC nonce to the owner signature, and submits the arm's circuit. The returned `txHash` identifies the confirmed call and `nextUseCounter` is the counter after it. A rejected or indeterminate submission must be reconciled with the live ACC before retrying; a caller must not assume funds were untouched after a transport failure. A Lace hosted JubJub authoriser needs a matching `withdraw-unshielded` consent mapping before enabling this method in Lace.

A shielded withdrawal uses the `inboxIndex` returned by `readShieldedHoldings`, the coin's lowercase color, and the recipient's lowercase 32-byte Zswap coin public key. For now `amount` must equal the selected coin's full value. A smaller amount would create change that this API cannot yet capture and republish safely, so it is rejected before signing. The owner session verifies the current account key and live device, reopens the selected inbox description, matches it to an ACC output and unique Merkle index, and signs a challenge that includes that qualified coin. The proof remains authoritative for whether the output is still unspent; hosts must reconcile spent descriptions after a confirmed call. The Passport service's fee-only sponsor rejects shielded offers, so a host must use a value-capable wallet for this transaction. `mn-passport-adapter-midnight-js` exports `createMidnightWalletPorts(walletProvider, midnightProvider)` to adapt such a wallet to the chain port. The hosted Lace JubJub adapter currently rejects `withdraw-shielded` because its consent flow and hosted handle lack the required witness path; a host must provide both before exposing this method there.

## Ports

`PassportPorts` injects a pinned `network` and `binding`, `credentials`, `authoriser`, `encryptionKey`, `chain` and `deployer`. `directory`, `records`, `holdings` and `random` are optional in the current type. Chain-facing ports include `Prover.proveTx`, `FeeSponsor.balanceAndSign` and `Submitter.submit`. `VerifiedHoldingSource` is required when a host offers JubJub viewing-key rotation: it must validate opened coin descriptions against chain-created outputs and select distinct held entries. An inbox ciphertext by itself does not prove a holding. A host implements these contracts instead of putting browser, service or Midnight dependencies into the account flow. The [port source](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/account/src/ports/index.ts) is the detailed type reference; [`account/testing`](https://github.com/input-output-hk/midnight-passport-sdk/tree/passport-acc-prototype/packages/account/src/testing) supplies fakes and contract suites.

`Chain.readAccount(address, { includeInbox: true })` also returns the ACC inbox values in ledger-index order, capped at 4096 entries, for flows that need to open sealed account keys. The default read omits the inbox. Both browser authoriser arms request this view to validate the viewing key.

`Chain.readAccount(address, { includeDevices: true })` returns up to 64 live device commitments. A rotation or device-management flow must resolve registered reader keys against this set before sealing a new account secret to them; inbox registrations alone are untrusted.

Shielded ACC withdrawals need a `QualifiedShieldedCoin` private witness with 32-byte nonce and color, unsigned 128-bit value, and unsigned 64-bit Merkle index. `createMidnightChain` accepts it only as `Chain.call({ heldCoin })` for a `withdraw_shielded*` circuit. The adapter snapshots the value for that call and refuses a different color requested by `held_coin`. It does not add the coin to proof-service metadata; remote proving still receives the serialized transaction preimage needed to produce a proof. The account API obtains this input from `QualifiedHoldingSource`. The hosted ACC handle does not yet accept this witness.

`createMidnightHoldingSource(indexer)` from `mn-passport-adapter-midnight-js` implements `VerifiedHoldingSource` using the Midnight ledger's contract-owned output commitment. The host supplies `enumerateContractActions(account)` and `queryShieldedOutputs(txHash)` from an indexer on the account's pinned network. The adapter selects the first inbox description for each distinct output the chain created for the ACC and ignores decryptable descriptions without such an output. Pass this source as `holdings` to `createBrowserPassport` when enabling JubJub rotation.

The same source also implements `QualifiedHoldingSource.selectQualifiedHeldCoins`. When the indexer supplies each output event's `index` (the Merkle position exposed by Lace's indexer), it returns the chain-matched coin with `mt_index` for `held_coin`. A missing or ambiguous index is rejected. This confirms that the ACC received the output; it does not establish that the output is still unspent. The host must reconcile spent outputs, make the qualified coin available inside the owner signing session, and rely on the proof to reject a stale spend. The current read-holdings method does not spend it.

`createHostedAccChain({ network, binding, readLedger, connectHandle })` from the same package adapts a host's existing ACC transaction handle to the account `Chain` port. Supply `binding` from the pinned `mn-passport-contract` registry as `{ id: network.bindingId, ...resolveBinding(network.bindingId) }`. A Lace host can supply its decoded ledger reader and `GatedContractHandle` instead of using the SDK's transaction-level prover path. The adapter checks the binding and manifest pin, refuses circuits absent from that binding, maps inbox and device entries, and refuses a finalized failure status or missing transaction ID. The host still owns the network-specific providers, proof, fee wallet, submission, and progress events. This seam has a fake-handle contract test, and the packed-package check compiles against Lace's exact generated ledger and handle types at PR #2845 head `cdfa9cfd`. It has not yet run inside Lace's hosted module.

`createMidnightGrantSource({ network, binding, openings, publicDataProvider? })` implements `ActiveGrantSource`, `ActiveGrantSnapshotSource`, `GrantDetailSource`, and `ActiveReadGrantTargetSource` from one pinned `acc-s3r1.1` ACC grant-map snapshot per read. The host supplies `openings.readReadPublicKey(account, grantId)` from its durable local grant records. The adapter checks each available read public key against the ledger's `read_pk_hash` (SHA-256 of the raw 32-byte key); a missing or mismatched opening stays in the target roster without a public key, so rotation reports it as unsealed. The snapshot and grant-detail reads return the ledger auth nonce. Hosts must keep the provider on the same network as the chain port and confirm transactions before treating submitted changes as settled.

`readVerifiedHoldings({ account, keyring }, { networkId, chain, authoriser, viewingKey, holdings })` is an additive account helper for a host that has already selected this device's sealed keyring from the live ledger. It checks the account and current `enc_key`, opens the inbox inside one `read-holdings` key session, and returns only opened coins whose inbox indices the chain-backed `VerifiedHoldingSource` confirms. It rejects duplicate, out-of-range, or non-coin selections. The caller supplies the keyring selection and indexer-backed holding source; the helper does not perform those host-specific steps or move funds. An empty inbox returns without a key session.

An opened JubJub or sealed P-256 `PassportAccount` offers `readShieldedHoldings(options?)`. It selects the sealed keyring from the current ACC inbox, confirms the recorded owner device still has a live entry, then uses the same verified holding source and `read-holdings` consent flow. P-256 also checks the selected passkey against the account record and opens its current envelope against the ledger `enc_key` before reading. The pinned Lace v1 inbox prefix lets JubJub return an empty list without a key ceremony when there are no coin-description entries. The host must inject `holdings`; the SDK does not trust a decryptable inbox description without a matching chain output.

`addJubjubAuthorisingDevice(input, ports)` is the lower-level, authorisation-only helper. It derives a new JubJub entry from the joining device's public key, checks the current owner's live entry and ACC binding, signs the pinned `add_device_with_jubjub` challenge inside an `add-device` key session, calls the circuit, then persists the advanced use counter. It sends no account keys. A host must not present that device as able to read holdings. `account.addDevice(reader)` validates the joining device's compressed signing key against its commitment, seals the viewing and roster secrets to its reader key, confirms both entries in the inbox, then enrolls the device. When a read grant is live, it first rotates both secrets, re-encrypts verified holdings, and reseals every active read grantee before delivery; it refuses an unsealable grant or an unregistered surviving device. The result returns the confirmed grant seals for the host's durable grant record. If enrollment fails after the key switch, the owner can reopen the new keyring and retry; an exact prior joining registration is accepted, while conflicting registrations remain refused. The joining host must know the ACC address out of band. A JubJub joiner can call `openAccountAt(address)` to verify its live device entry, current registration and sealed viewing key, then save its directory hint. The authorising-only hosted addition has synthetic localnet evidence; sealed enrollment still needs a compatible hosted roster-read consent contract. See the compatibility matrix.

For P-256, `account.addDevice` requires a pinned `acc-s3r1.1` binding with `challenge_add_device_with_p256`, a chain port that reads the live device set and inbox, a key session, and a complete active read-grant source. It checks the joining P-256 key and WebAuthn policy, current owner passkey, live owner entry, existing registrations and stable roster. If read grants are live, it additionally requires verified holdings, rotates the viewing and roster keys inside the approved add-device session, and refuses enrollment unless every active grantee can receive a fresh seal. It then appends the joining device's envelope and type `0xd5` registration before signing `add_device_with_p256`, and confirms the new commitment is live. A failed delivery after rotation leaves the old owner able to reopen the fresh keyring and retry; a failed sealed-entry publication can also be retried while the joiner is not live. This owner call does not register the joining credential with the account directory. The joining host can call `openAccountAt(address)` with its passkey and passkey-derived reader; the API verifies its live entry and opens the sealed key against the ledger `enc_key`. The host must retain or transfer the ACC address. The demo exposes a two-profile handoff UI; the complete real two-browser passkey ceremony remains a manual qualification step.

Sealed P-256 accounts also expose `account.rotateViewingKey(options?)`. The host supplies a chain-backed `holdings` source and a complete `readGrants` target source. Inside a passkey key session, rotation opens the current envelope, resolves each registered reader against the live mixed-curve device roster, re-encrypts verified holdings, and appends fresh device envelopes and available read-grant seals before signing `rotate_enc_key_with_p256`. It checks the ACC key, nonce, roster and inbox before the key switch. The result lists grant seals and any active grant IDs that could not be sealed; the host must reconcile those records. An interrupted multi-transaction rotation requires inspecting the ACC key and inbox before retrying. The demo now supplies chain-backed holding and grant readers and exposes reviewed rotation. P-256/mixed-device and read-grant rotation/revocation have localnet proof evidence; unavailable surviving openings still cause refusal.

`removeDevice` runs inside a `remove-device` key session that names the live survivors before any key change. Both JubJub and sealed P-256 reject self-removal, an absent target, an unregistered or ambiguous surviving reader roster, and any reader or signing key shared with the removed device. P-256 also refuses removal if an active read grant would deliver the fresh key to the removed reader. They append new envelopes and registrations before changing `enc_key`, then use their pinned removal circuit and confirm that the target left the live ACC set. The removed reader receives neither the fresh viewing secret nor the fresh roster key. This is a multi-transaction operation: if removal fails after the key switch, the host must inspect the live device set and inbox and reconcile the pending removal before retrying. A node-backed P-256 run now covers enrollment, both key openings, key rotation, removal, continued owner access and rejection of the removed passkey. A browser passkey ceremony remains to be exercised manually.

The grant holder path reads `createMidnightGrantSource(...).readGrantSpendContext(account, grantId)` from one ACC snapshot. `checkUnshieldedGrant(intent, live, pure, nowSeconds)` accepts only a recipient-pinned unshielded spend and verifies the derived ID, object and spent commitments, operation, expiry, per-call limit and remaining cap. `spendUnshieldedWithGrant(intent, ports, options?)` requires a separate JubJub grantee key, an explicit host review of the exact public transfer fields, and a value-capable chain port. It rechecks the grant before submission, builds the pinned challenge, and confirms the live grant nonce and spent commitment afterward. A submitted call whose settlement is uncertain throws `SubmittedGrantSpendError` with its transaction hash and `retryable: false`; reconcile that transaction and the live grant before any retry. A [node-backed localnet run](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-p256-grant-holder-node.json) issued a fixed-recipient grant from a P-256 owner, spent four NIGHT units through an independent JubJub grantee, revoked it and refused a later use. The browser demo routes owner and holder unshielded withdrawals through a localnet-only, circuit-limited value-capable funding wallet endpoint; the fee-only sponsor still handles ordinary calls. It includes a separate grantee passkey, opening handoff, fixed-recipient review and spend view. The browser route and passkey ceremony still need a manual localnet run.

`prepareJubjubGrant(input, pure, random?)` checks a Lace-shaped JubJub grant request and derives the grant ID, first free slot, scope digest and object commitment with the pinned ACC pure circuits. Supply the live active grant IDs and current POSIX seconds from the account's network; the function cannot verify a caller-provided roster. It accepts decimal strings for amounts, rejects unsafe grantee and read public keys, enforces the contract's reserved window fields and the 16-active-grant client limit, and draws a fresh 32-byte scope salt. The returned `scopeArgs` follow `issue_grant_with_jubjub` declaration order. This is preparation only: the owner flow must pin the origin, obtain consent and the owner's signature, submit and settle the proof, and persist sealed bookkeeping.

`issueJubjubGrantCall(input, ports)` submits an owner-signed grant. Before prompting, it checks local record presence, reads active grant IDs and the ACC auth nonce from the host's chain-backed `ActiveGrantSnapshotSource`, and prepares the scope only if that nonce matches the signing view. Inside one `issue-grant` key session, it confirms the device, signs the generated challenge, and rechecks the nonce and ID set before requiring `GrantIssueJournal.stage` to persist the opening. A read grant requires `rotateBeforeIssue` in the same owner session; the helper reads the changed nonce and unchanged grant roster before signing. The host must reconcile the submitted grant and publish its sealed records before presenting it as active. The journal must survive process restarts.

`publishJubjubGrantBookkeeping(input, ports)` finishes a staged grant. It waits for the grant ID in the live ACC map, opens this device's inbox, and appends missing sealed grant and object records. For a read grant it also seals the current viewing secret to the staged read key and confirms the view record in the ACC inbox. A retry appends only missing parts; the durable journal is cleared only after all required records are confirmed. If an accepted append does not appear within the polling bound, inspect chain state before retrying. The returned `sealedReadGrant` is ciphertext for the host's agent policy export.

`issueAndPublishJubjubGrant(input, ports)` composes submission and publication and returns `status: 'active'` only after the live grant and sealed records are confirmed. A read result includes the pre-issue `rotation` and the new grantee's `sealedReadGrant`. A failure after issue submission throws `SubmittedGrantSettlementError` with the accepted transaction hash and grant ID while leaving the opening staged. Use `publishJubjubGrantBookkeeping({ hint, grantId }, ports)` to resume after checking the live ACC roster. Do not issue a new grant merely because publication timed out.

`account.issueGrant(scope, options?)` exposes this settled path to both account arms. A browser host passes `grants`, `grantJournal` and `records` to `createBrowserPassport`; its passkey `rpId` becomes the pinned grant origin. Revocation additionally requires `grantDetails`, which `createMidnightGrantSource` also supplies. Other hosts pass those ports plus `grantOrigin` to `createPassportAccounts`. The DApp supplies only the scope, so it cannot choose the origin used in the grant ID. Hosts must recover staged submissions from their durable journal after a crash and reconcile the live roster before resuming publication. This method rejects unsupported scopes before a key ceremony.

For crash recovery, implement `GrantRecoveryJournal.pending(account)` and call `account.recoverPendingGrants()`. It publishes staged grants already active in the ACC and returns absent ones as `unsettledGrantIds`; it never submits a new issue call. Keep those openings durable until chain state explains whether the original issue landed. Invalid or duplicate pending IDs are refused before a key session. `recoverPendingJubjubGrants` and `recoverPendingP256Grants` expose the same path to hosts using the lower-level ports.

`publishP256GrantBookkeeping({ hint, grantId }, ports)` is the lower-level publication step for an already accepted P-256 issue on `acc-s3r1.1`. The host must durably stage the grant opening and supply the active grant source, journal, account record store, sealed viewing key, chain and P-256 authoriser. It waits for the live grant, validates the selected passkey and staged opening, appends only missing sealed grant records, and marks the journal published after the inbox settles. Read grants also receive a seal for the current ACC viewing key. This helper never submits an issue.

`issueP256GrantCall(input, ports)` submits the pinned P-256 issue after validating the scope against an auth-nonce-pinned live roster and durably staging its opening. A read grant requires a host `rotateBeforeIssue` hook in the same owner session; the hook must preserve every active read grantee. `issueAndPublishP256Grant(input, ports)` composes that call with the publisher and returns active only after sealed records settle. If publication fails after submission, `SubmittedGrantSettlementError` carries the grant ID and transaction hash for a publication-only retry. A sealed P-256 account now exposes the same `account.issueGrant(scope)` and `account.recoverPendingGrants()` methods as JubJub when the host supplies records, grants, a durable journal and a trusted origin. Read issue additionally requires chain-backed holdings and read-grant targets; it refuses a key rotation that leaves any live reader unsealed. The browser demo does not provide those host ports yet.

`createMidnightGrantSource` also exposes `GrantCommitmentSource.readGrantCommitment(account, grantId)`, returning the live ACC object's commitment, read-key hash, read flag, active flag and auth nonce from one checked snapshot. Both grant publishers require this port and reject a staged opening that differs from the current on-chain grant before appending or marking it published. Hosts pass it as `grantCommitments` alongside `grants` and `grantJournal`; the inbox alone is not proof of the current grant's scope.

JubJub create, device enrollment, grant issue, bookkeeping publication, and revoke pass a consent descriptor to `Authoriser.withKeySession`. The descriptor carries Lace's creation lock choice, account address, device commitment, or grant scope, slot, salt, and digest as appropriate. Publication reloads the durable opening after the session begins and refuses a scope that changed since consent. A hosted signer still needs a host adapter for branded Lace values and its transport; this descriptor alignment alone is not a tested Lace integration.

`revokeJubjubGrantCall(input, ports)` submits the pinned owner-signed revoke circuit for a grant whose live ACC record is active and has no read permission. Its chain-backed `GrantDetailSource` must expose the read flag and auth nonce; a read grant is refused because revocation must first rotate the viewing secret and reseal it to remaining authorised readers. The helper checks the grant and nonce again after signing, advances the local device counter after the accepted call, and returns `status: 'submitted'`. The host must confirm the inactive grant tombstone before reporting a completed revocation.

`revokeAndConfirmJubjubGrant(input, ports)` performs that confirmation for an unshielded grant and returns `status: 'revoked'` only after the live grant source reports an inactive tombstone. It reports `GrantRosterUnsettled` if the bounded poll expires; a host should inspect chain state before retrying an ambiguous submission. `account.revokeGrant(grantId, options?)` also handles a read grant: inside one `revoke-grant` key session it checks the live grant, rotates the random viewing secret to registered devices and surviving read grantees while omitting the revoked grantee, re-encrypts verified holdings, signs the pinned revoke circuit, then confirms its inactive tombstone. The result's `rotation` contains the new seals and reports any surviving grant it could not seal. If the revoke call fails after rotation, the key change may still have landed; inspect the chain and the sealed ACC inbox before retrying or updating host grant policy.

P-256 `account.revokeGrant` signs `revoke_grant_with_p256` on `acc-s3r1.1` and confirms an inactive live tombstone. For a read grant, it requires sealed keys, chain-backed holdings, live grant details and read targets; it rotates the secret before signing, excludes the target grantee from new seals, and returns seals for surviving read grantees in `rotation`. It refuses the key switch if a surviving read grantee lacks a usable seal. A spend-only grant uses the same pinned revoke circuit without rotation. If submission fails after rotation, inspect the ledger key, inbox and grant map before retrying.

`account.revokeAllGrants(options?)` uses the pinned `revoke_all_grants_with_jubjub` circuit. The host supplies `grantRoster` with the complete chain-backed map, including tombstones and `grant_generation`; `createMidnightGrantSource` implements this port. With live read grants, the flow rotates the viewing secret in the same owner session, re-encrypts verified holdings, and delivers the new key to live devices only. It checks that the grant roster and generation remain unchanged across rotation and signing, then returns `status: 'cleared'` only after the map is empty and its generation advances. An interrupted rotation or unsettled submission requires chain and inbox inspection before retrying.

P-256 `revokeAllGrants` uses `revoke_all_grants_with_p256` on `acc-s3r1.1`. It requires a complete live grant roster and, when read grants are active, sealed keys, verified holdings and a matching complete read-target source. It rotates the viewing secret to live devices while sealing no read grantee, verifies the grant map remained unchanged, signs the binding's challenge with the account credential, and rechecks the roster and ACC nonce before submission. It reports `cleared` only after an empty map with the next generation is observed. The result includes the prior rotation when one occurred. Hosts must inspect chain and inbox state before retrying an unsettled submission after rotation.

`sealActiveReadGrants(input, ports)` prepares read-grant delivery records for a new ACC viewing key. Its chain-backed target source must include every active read grant, return the ACC auth nonce, and verify each available read public key against the on-chain hash. The helper refuses a stale nonce, omits a grant being issued or revoked, validates each sealed inbox record against its grant ID and new key, and reports grants whose read key could not be sealed. Revoke-all validates the roster with `exceptAll` and seals no grantee. Rotation, read issue and read revoke use it to preserve authorised readers before a key switch. Durable recovery of interrupted rotations remains release work.

The `mn-passport-service` package now exports a bounded `createMemoryJobStore` and `jobsRoute` for `GET /v1/jobs/{id}?after={cursor}`. A submitted job is pollable before work begins; polls return only events after the cursor plus its current result or sanitized error. The memory store is a standalone reference implementation and loses jobs on restart. A deployed backend should inject a durable `JobStore` with the same contract. `v1ChainRoute` serves `POST /v1/prove-tx` and `/v1/deploy` as `202 {jobId}` plus synchronous `POST /v1/sponsor/balance` and `/v1/sponsor/submit`. The demo serves these routes alongside its legacy paths, using one proof/deploy queue and one deployment cap. `serviceConfigRoute` answers `/v1/config` with the pinned network, binding, manifest hash, API version and sponsor public keys. `pinnedZkRoute` verifies the full artefact tree before serving the binding-specific `/v1/zk/{bindingId}` URL that config advertises. The demo browser uses the versioned routes. On a `/v1/accounts` miss it reads the legacy `/accounts` registry so existing demo accounts can reopen; new hints go only to `/v1/accounts`.

The same package exports `sponsorPolicy`, `viewOfLedgerTx`, and `guardedBalance`. An operator injects the ledger deserializer, current allowlist of Passport ACCs, and its own funded wallet through `GuardedBalanceDeps`. The policy refuses shielded or unshielded offers, Dust actions, non-call actions, unlisted contracts, and non-Dust value imbalances before it invokes the wallet. Fee sponsorship does not transfer value into an ACC; that needs the separate funding service.

`mn-passport-adapter-service` exports `remoteV1Prover`, `remoteV1Deployer`, and `remoteV1Sponsor`. The first two submit a v1 job and poll it with a cursor; they forward validated service progress through `onEvent`, honor `signal`, enforce a total timeout, and preserve the service's error code. The sponsor uses the synchronous v1 fee endpoints. `fetchCheckedV1Config` checks the advertised network, binding, manifest, service API version and binding-specific artefact URL against host pins before a host uses these ports. The standalone browser demo uses these clients without changing the account core.

The separate `mn-passport-adapter-service/faucet` subpath exports `remoteFaucet` for `POST /v1/faucet/fund`. A caller supplies a stable UUID, pinned network/binding/manifest, ACC address, allowlisted asset color and decimal amount, plus a callback for fresh authorization headers. The result includes the transaction ID and confirmed credited ACC balance. `apps/passport-funding-service` composes the route with a dedicated wallet and durable reservations; the demo CLI can start it with `--funding`. Only the recorded non-native unshielded asset path is advertised, pending node-backed tests for other assets.

### Shielded deposit sender boundary

`depositShielded(request, ports)` from `mn-passport-account` prepares the pinned ACC `deposit_shielded` inputs and confirms the new encrypted coin description in the live inbox. The request contains the ACC address, stable UUID `requestId`, 32-byte asset color, positive 128-bit amount, and a stable 32-byte coin nonce. The host supplies `chain.readAccount`, `sealCoin` (for example `sealInboxCoin` from `mn-passport-keys`), `sender.depositShielded`, and `sleep`. The sender owns the value-bearing wallet, proof, fees, submission, and durable request-ID deduplication. It must prove and submit `deposit_shielded(coin, entry)` with the supplied coin and 192-byte entry. The account package cannot fund a deposit on its own.

The flow checks the live ACC `enc_key` before sealing and again before submission, then returns the transaction ID and inbox index after observing the exact entry on chain. If confirmation expires after submission, the error includes the transaction ID: reconcile the sender transaction and ACC inbox before retrying. A key rotation between the second check and on-chain execution can still invalidate the envelope; the sender or contract adapter must handle that race. The [localnet probe](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/sdk-shielded-deposit-node.mjs) used `createHostedAccChain` with the pinned upstream wallet's real `callTx` handle to deposit a non-native shielded coin, confirmed its inbox entry, and opened it with the upstream reader. Its [run record](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-shielded-deposit-node.json) records the transaction and binding. This single-use probe has no durable request-ID journal. A funding-service HTTP endpoint for shielded deposits remains to be built.

A deployed JubJub `AccountHint` carries two sealed 192-byte `keyEntries` until they have been appended to the ACC inbox. They contain no raw viewing secret. An active hint recovered by address needs no boot salt or pending entries. A directory response is an untrusted pointer: the owner flow must match its credential and device key to the selected passkey, check the on-chain device entry, and open an envelope against the ledger's `enc_key` before completing or accepting it.

### JubJub viewing-key port

`AccountViewingKey` is the port for Lace's random ACC viewing secret and device envelopes. `recipeDeviceKeyring(prfSource)` from `mn-passport-keys` implements it: `readerPublicKey`, `createKeys`, `sealToDevice`, `openInbox`, `sealGrant`, `reencryptInbox`, and `sealView`. The keyring opens the current sealed secret only inside a passkey session, checks it against the ledger's `enc_key`, and clears it after each operation. The account flow must confirm that any joining reader belongs to the device entry being enrolled, and that readers kept during rotation are unique live devices. `openInbox` returns decrypted coin descriptions, device registrations and grant bookkeeping, or `null` for unrelated entries.

The JubJub authoriser also supplies `devicePublicKeyHex()`, a validated compressed point for the device registration. The WebAuthn credential adapter can select a discoverable passkey for a pinned PRF ceremony before a P-256 key is chosen; a JubJub flow verifies the resulting device key against the on-chain entry and the directory hint.

Both browser authoriser arms use `AccountViewingKey` to create a random account secret, seal it to the passkey-derived reader, and validate it against the live ACC encryption key. They persist sealed entries before activation so `openAccount` can resume an interrupted create. Both rotation flows send new device envelopes and active read-grant seals before switching the ledger key, and refuse concurrent key, device-roster or read-grant-roster changes. Both read-grant issue paths require host supplied chain-backed holdings and read-target sources; the browser composition does not provide them by default. The `encryptionKey` port is retained only for explicit legacy P-256 hosts; the browser composition refuses their old account hints until migrated. See [key roles and recovery]({{ '/keys/#account-viewing-secrets-and-recovery' | relative_url }}).

`openGrantView(readSecret, { grantId, account, seal, expectedEncKey })` from `mn-passport-keys` lets a read grantee open the 94-byte seal returned by grant issue or viewing-key rotation. Supply the `expectedEncKey` from the live ACC ledger; the function returns `null` if the opened secret does not match it, or for a wrong reader, altered seal, account or grant ID. Clear the returned 32-byte viewing secret after use. The seal carries no proof that its grant is still active; verify the live grant map before using read access.

## Events and cancellation

Each step reports `start` and exactly one `end` or `error` with the same `flowId` and `id`. `PassportEvent` includes `step`, `phase`, timestamp `at`, `clock`, optional `durationMs`, safe detail fields and an error code. Relevant steps include `passkey.create`, `deploy`, `activate`, `prove`, `sponsor.submit` and `chain.finality`. `signal` ends a flow with `Aborted`; it cannot reverse an already submitted transaction. See [events.ts](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/protocol/src/events.ts).

## Errors

Catch `PassportConnectorError` and use its `code`, `retryable` and `step` fields. Do not branch on message text. Codes include `UserCancelled`, `UnsupportedAuthenticator`, `WrongPasskey`, `AccountNotFound`, `SponsorRejected`, `ProverUnavailable`, `ArtefactIntegrity`, `ApiVersionUnsupported` and `InternalError`. The full table and Lace code mapping live in [errors.ts](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/protocol/src/errors.ts).

`createPassportConnector(seams)` is a deprecated compatibility bridge. New integrations use `createPassportAccounts(ports)`.

## Browser composition

`createBrowserPassport(config)` from `mn-passport-adapter-browser` supplies WebAuthn credentials,
the P-256 authoriser by default, or the JubJub authoriser and device keyring with `arm: 'jubjub'`. The host passes a pinned `NetworkConfig`,
the ACC binding, prover, sponsor, submitter, deployer and directory ports. The Midnight call
pipeline loads on the first chain operation; its network id is set for each read and call. The
`sponsorKeys` field carries the fee payer's public coin and encryption keys required by midnight-js.
See [BrowserPassportConfig](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/packages/adapter-browser/src/compose.ts).

`mn-passport-adapter-service` supplies `remoteProver`, `remoteSponsor` (both fee sponsor and
submitter), `remoteDeployer`, `remoteDirectory` and `fetchCheckedConfig`. The demo uses these clients
against the versioned service. `remoteDirectory` uses `/v1/accounts`; the standalone service serves it through `directoryRoute` and a single-process file store. Hints are write-once except a `deployed` to `active` status change. A supplied ownership proof is refused unless the host injects an `OwnershipVerifier`; the standalone flow currently writes without one. The directory is an untrusted pointer, and the account core checks its answer against the ACC ledger before using it.
