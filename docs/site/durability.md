**Local milestone implementation for #230 and #239; not included in published RC5.**
The binding remains `acc-s3r1.1`. This work adds an opt-in account API and protected
persistence helpers. The default browser composition and demo owner buttons still
use the original account API. Integrating a journal alone does not make a remote
transaction or deployment service crash durable.

## Choose the right recovery path

| Situation | Supported action | Required material / refusal |
| --- | --- | --- |
| Page reload after settled creation | Open the known ACC with the enrolled credential | The selected key origin must still derive the original reader; the current sealed envelope must open the ledger key |
| Owner mutation interrupted with a protected continuation | `createDurablePassportMutations(...).resume({ id })` | Same pins and original intent, fresh host approval, exact chain reconciliation and a host submission outcome source |
| Transaction outcome unknown | Stop and reconcile the original request | No blind retry, new mutation ID, replacement generation or assumption that an empty indexer response proves no send |
| Crash or ordinary key-origin exception before durable output acknowledgement | Refuse with `MutationUnsettled` | The ordinary key port cannot recover this output atomically. Recover the original output in the owning host, or reconcile manually; the SDK does not draw another key |
| Browser grant journal lost, published records complete | Recover published bookkeeping with the **original issuing reader** | Live commitment, trusted origin, read-key hash and stable chain snapshot checks must all pass |
| Another enrolled device can open the ACC but cannot open those grant records | Restore the original reader or its protected publication journal | Shared ACC viewing access does not imply possession of a device-reader-encrypted grant opening |
| Pending grant never published completely | Resume from its original encrypted grant journal | Chain reconstruction cannot invent missing salt, object opening, full scope or grantee signing secret |
| Every enrolled key origin lost | Unsupported total-loss recovery | Not implemented by this journal or the retained binding policy; tracked separately in #240 |

## Durable owner API

`createDurablePassportMutations` is exported by `mn-passport-account` and supports
four intents: `create`, `rotate`, `add-device` and `remove-device`. Both P-256 and
JubJub routes run the existing checked account flows. The whitelist of persisted
chain effects is deployment, activation, sealed inbox append, encryption-key
switch and device-entry addition/removal. Value transfers, private `held_coin`
witnesses, standalone recovery circuits and arbitrary circuit calls are excluded.

A host supplies the usual `PassportPorts`, plus:

- `MutationJournal`: authenticated, confidential, atomic compare-and-swap storage;
  resolve a write only after it is crash durable. A listener or ordinary file overwrite is insufficient.
- `MutationOutcomeSource`: authoritative resolution for the **exact** network,
  binding, mutation request ID and intent digest. `confirmed` includes the final
  transaction ID, or deployment address and complete wave IDs. A deployment
  confirmation attests every required wave and the original retirement choice.
  `not-submitted` additionally requires `fenced: true`: every earlier sender is
  stopped/fenced and cannot broadcast later. A currently empty receipt table or
  ledger is insufficient. Uncertain, pending, partially deployed and rejected
  calls without this guarantee remain `unknown`.
- `MutationConsent`: authenticate and approve the original intent on **each**
  invocation, including resumption. Original `retireAuthority`, removal target,
  joining reader and owner flow descriptors are retained. Existing key-session
  policy remains in force; the coordinator does not widen hosted signing scopes.

Every `CallRequest` and `DeployRequest` generated by this coordinator carries
`mutation: { requestId, intentSha256 }`. The host transport must persist that
correlation before it can lose a broadcast response. The opt-in [Node host transport]({{ '/host-durability/' | relative_url }}) now
provides persisted submission and deployment-wave continuation. Default Midnight/service
compositions do not enable it automatically. If they ignore the
metadata, the host must return `unknown` for an interrupted submission.
A multi-wave deployer needs its own durable wave journal; an interrupted partial
deployment must not be reported as a completed deployment or deployed again.

### Host composition

This example uses an already selected, authorised key origin. It does not enrol
a new browser credential. For durable creation, `ports.credentials.create` must
resolve that selected credential; an ordinary WebAuthn enrolment ceremony before
there is a journal key needs separate host orchestration. A lost credential
creation result is refused just like a lost sealed key output.

```ts
import { createDurablePassportMutations } from '@input-output-hk/mn-passport-account';
import type {
  PassportPorts, PrfKeySource, MutationByteStore,
  MutationConsent, MutationOutcomeSource,
} from '@input-output-hk/mn-passport-account/ports';
import { encryptedMutationJournal } from '@input-output-hk/mn-passport-keys';

export function durableOwner(
  ports: PassportPorts,
  selectedKeyOrigin: PrfKeySource,
  store: MutationByteStore,
  consent: MutationConsent,
  outcomes: MutationOutcomeSource,
) {
  const pins = {
    networkId: ports.network.networkId,
    bindingId: ports.network.bindingId,
    manifestSha256: ports.network.manifestSha256,
    scheme: ports.authoriser.scheme,
  };
  return createDurablePassportMutations({
    ports, consent, outcomes,
    journal: encryptedMutationJournal(pins, selectedKeyOrigin, store),
  });
}
// Host generates a unique, durable 16-byte lowercase hex id before starting.
// const result = await owner.run({ kind: 'rotate', account: address }, { id });
// After interruption, reuse the SAME id:
// const result = await owner.resume({ id });
```

In Node, `fileMutationByteStore(privateDirectory)` from `mn-passport-service`
supplies a local POSIX byte store. It uses private immutable revision files,
fsync and atomic hard-link publication. Concurrent writers cannot overwrite a
revision; corrupt latest revisions never fall back to an older revision. A killed
writer may leave an unreferenced temporary file, which is ignored. Filesystem
rollback by an attacker, network filesystems and operator deletion are outside
this store's guarantee. A stronger host must anchor revisions in trusted storage.
Do not put the directory in a web root, Git, shared cache or public backup.
Records are bounded to 8 MiB and 512 transcript steps. Repeated snapshots can
exceed this bound even within the ledger entry limits; oversized continuations
refuse and require explicit host reconciliation, never truncation or key replacement.
Browser hosts need an actual atomic durable store, such as an appropriately
implemented IndexedDB adapter; `localStorage` is not the supplied mutation store.

### State and restart rules

| Durable state | Next safe action |
| --- | --- |
| Pending intent | Preserve id, arm, network, binding/manifest and original consent/lock choice |
| Prepared step | Check the recorded frontier before beginning the next effect |
| Running sealed-output / credential step | Refuse if the original result was not committed; no replacement generation |
| Running chain effect | Ask the host outcome source. Confirmed effects must match the exact predicted ACC state. A fenced no-send may replay the same request |
| Done step | Reuse its original sealed output, signature or public result. Recheck key identity and verified holdings where required |
| Cancelled | Preserve everything. Submitted transactions remain submitted; a newly approved `resume({ id, resumeCancelled: true })` is explicit |
| Complete | Return only after checking the recorded chain frontier and final local hints. A missing local hint can be restored; a conflicting record needs explicit reconciliation |

The frontier includes `booted`, `authNonce`, `deviceEpoch`, current `encKey`,
complete inbox and sorted device-entry set. It is bounded to the supported spec-3
ledger (4096 inbox entries, 64 device entries). Before another effect or completion,
the current ledger must match. Stale/changed rosters, wrong generations, lagging
confirmation views, ambiguous registrations and missing read-grant openings stop
the flow. A rejected reconciliation cannot be converted into UI success.
`inspect(id)` reports the **stored journal phase**, not current chain acceptance;
use successful reconciliation before presenting a current mutation as settled.

### Storage, versioning and audit

The v1 protected document retains original intent, pins, revision, account-local
salt/flow entropy, transcript digests and results, submitted request arguments,
full ledger snapshots, sealed key outputs and final transaction identifiers.
It contains sensitive linkage and boot material even though raw PRF, signing,
reader and viewing secrets never leave the key ports. It is **not a public log**.
`encryptedMutationJournal` uses domain-separated PRF derivation and AES-GCM,
binds id/revision/pins in associated data, and erases temporary raw key/plaintext
byte buffers. JavaScript object/string memory is not a secure-erasure guarantee.

Unknown versions, malformed wire values, mismatched pins and corrupt authentication
fail closed. No implicit v1-to-future-version migration is supplied. A future
migration must authenticate the old record and preserve its original intent,
outputs and unresolved receipts; incompatible transcript changes need a new schema
or an explicit refusal. Existing grant journal versions 1 and 2 and envelope suites
1 and 2 remain readable under their existing checks.

`inspect` exposes only id, revision, phase and completed/unresolved counters.
Use this allowlist for public audit. Never log the document, port inputs, error
causes, openings or plaintext backups. Cancellation and resumption pass through
host authentication; there is no new raw backup/export API. Existing explicit
owner grant handoff remains a separate consented operation.

## Reconstruct published grant bookkeeping

`createGrantBookkeepingRecovery({ networkId, origin, chain, viewingKey,
commitments, pure })` is exported by `mn-passport-account`. Invoke `recover(account,
grantId)` inside the selected key origin's approved session. It opens the current
ACC key context and matching published `grant` plus `object` parts, deduplicates
identical records, rejects conflicts, then checks:

1. Derived grant ID from account, grantee, **trusted host origin** and slot.
2. Object commitment from the original scope salt and object opening.
3. Read-key hash and active read/spend status against the live grant.
4. Unchanged full ACC snapshot and matching grant `authNonce` during the operation.

The result is `GrantBookkeeping`, not a `StagedJubjubGrant`: full issue scope,
scope digest, caps/expiry context and private grantee signing capability are not
fabricated. `readReadPublicKey` can supply the opening source for
`createMidnightGrantSource`. That adapter retains the complete active read-grant
roster and independently checks the public key hash. A missing opening must raise
or remain an unsealable target; it must never become an empty roster.

The demo tries its existing encrypted journal first, then this authenticated
published-record path with the selected reader. Missing/corrupt local entries
and wrong key origins are not silently replaced. Its explicit grant handoff still
requires the full local staged opening; reconstruction does not manufacture one.

## Qualification and remaining boundary

Fast tests cover codec/storage corruption, CAS races, cancellation, unknown
outcomes, lost key-output refusal, selected fresh-process restart cases and grant
reconstruction/rotation. Run the complete generated-contract crash matrix outside
the required fast PR lane:

```sh
nix develop -c pnpm run build
nix develop -c node scripts/qualification/mutation-matrix.mjs /private/evidence/mutations.json
```

Each worker is a new process with a synthetic key origin and protected filesystem
journal. Its chain transport executes the shipped generated contract with actual
software P-256/JubJub signatures. It knows its atomic local sends; this is **not**
a model for inferring remote no-send from absence. Source/runtime hashes must stay
unchanged during the matrix. The receipt counts expected safe refusals separately
from resumptions. Cases cover all instrumented submission/receipt and material
boundaries for creation, rotation, enrollment and entry removal in both arms.
Intended surviving readers must open the final key; the removed reader must fail.

This is simulator/process evidence without proofs, funds, actual passkey providers
or a durable hosted deployment service. The matrix uses an empty active read-grant
roster; separate tests verify reconstruction, active-read delivery and refusal.
Full combined live-proof/host/provider interruption qualification remains open
under #230/#231/#232. General recovery through a missing key-origin output,
complete compromised-key retirement, partial shielded spends and full Lace
compatibility remain unsupported. See [Qualification]({{ '/qualification/' | relative_url }}).

## Node host continuation

The next local slice adds [durable host submissions and deployment waves]({{ '/host-durability/' | relative_url }}),
including an authenticated opt-in RPC, encrypted authority/transaction storage,
revision fencing and exact original deployment transaction reuse. The default
demo owner API is unchanged; proof-backed host interruption acceptance remains open.


### Concurrent deposits and unresolved material

Exact ledger snapshots include the inbox. A permissionless payment or another
caller can change that frontier and permanently stop a protected continuation;
there is no automatic inbox-extension reconciliation. This can occur after a
transaction confirmed. Original receipts/keys remain protected; a new ID is not a
repair. Key-origin throws, not only process death, may also leave an unavailable
original result. No generic exception proves no output. Pre-registration proving
failures and expired native bytes retain their explicit unresolved limits.

Known-address JubJub opening verifies the explicitly selected ACC and preserves
any earlier write-once directory hint. That hint may name another account; it is
not silently repointed. A later directory-selected account can therefore differ
from the explicitly selected address. Hosts should display the selected address
and use known-address opening again for that account.
