## Scope and status

This handover describes **localnet NIGHT funding** in the published `0.1.0-rc5` preview.
The nine private SDK packages and the RC5 funding image include the implemented path;
[RC5 release notes]({{ '/release-notes-rc5/' | relative_url }}) and the
[publication receipt](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/docs/release/rc5-publication-receipt.json)
record exact versions, immutable image digests and the published-image deposit/replay check.
Do not infer production or full Lace compatibility from this localnet evidence. The pinned ACC
is `acc-s3r1.1`, exported from Passport revision `6458ed5`, with manifest SHA-256
`77fb9c17b0d59047456c43115d9a58f5cb99a226ee73b6b974fd724930c3153f`.

The person who opened an ACC in the demo has confirmed that the **Fund Passport account** button credits it. A node-backed local run also returned a preparation transaction, deposit transaction, and increased ACC NIGHT balance. Replaying its completed request ID returned the same transactions and balance without a second deposit. This is live localnet evidence in addition to the automated checks; it does not cover other networks or wallet versions.

## The value path

1. The browser on `http://localhost:5173` creates or opens an ACC with a passkey. The passkey controls ACC authorisation and the sealed viewing secret. The separately derived built-in HD wallet is read-only in this demo and does not supply the deposited NIGHT.
2. With `demo up --funding`, the page reads the offered assets and ACC unshielded balances through `GET /v1/demo/funding` on the Passport service (`127.0.0.1:8787`). It defaults to NIGHT when the policy offers it. Balances and fixed deposit amounts are displayed in **smallest units**.
3. Clicking **Fund Passport account** sends the ACC address, selected asset color and a browser-held UUID to `POST /v1/demo/funding`. This localnet-only proxy checks the demo origin and deployed-account log, then adds the private bearer token and fixed policy amount server-side. The browser never receives the funding seed or token.
4. The separate funding process (`127.0.0.1:8789`) checks the request pin, bearer token, deployed ACC, and asset limits. It durably reserves the request ID before touching its wallet. Its wallet backend checks ACC `spec_version = 3` and reads the pre-deposit balance.
5. For localnet NIGHT, the funding wallet makes an exact-value self-transfer to create an input without a change output. It then invokes the pinned ACC's `deposit_unshielded` with that value, submits the transaction, and polls the ACC ledger until the balance rises by at least the requested amount. The response includes the deposit transaction ID, optional preparation transaction ID, and confirmed ACC balance. The page refreshes NIGHT and test-token balances and records the public request/response timeline in **Operation trace**.

The preparation is needed because the pinned node rejected a NIGHT deposit with a wallet-generated change output under its fee budget. The funding process uses a separate wallet instance; on the standalone `undeployed` network its default seed is the **public genesis development seed** also used by the sponsor. Other networks require an explicitly provisioned dedicated funding seed, and NIGHT is refused there until separately qualified. The fee sponsor endpoint continues to reject value-bearing calls.

## Run and inspect

Follow [AGENTS.md](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/AGENTS.md) for Nix, Docker memory, the pinned contract export, and the localnet ports. Create a private bearer-token file and asset policy using the [funding service guide](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/apps/passport-funding-service/README.md). Then run:

```sh
export PASSPORT_FUNDING_TOKEN_FILE=$HOME/.midnight-passport/funding-token
export PASSPORT_FUNDING_ASSETS_FILE=$HOME/.midnight-passport/funding-assets.json
nix develop -c node scripts/demo.mjs up --funding
```

Open `http://localhost:5173/` (the passkey origin matters), create or reopen an ACC, and use the funding button. The `8789` root path is not a UI; use `/healthz` for readiness. The funding API is authenticated. Expand **Operation trace (requests and responses)** and use **Copy full log** for a colleague-facing record. It includes action stages, connector events, request/response metadata, account and wallet addresses, deposit ID, preparation ID and balances; it excludes raw passkey results, PRF output, viewing secrets, wallet seeds and bearer tokens. The trace begins at page load, so repeat the flow in one session if the complete sequence is needed. `node scripts/demo.mjs fund --help` documents the operator CLI.

The local demo now also exposes an owner-authorised unshielded withdrawal. Enter a network-matched `mn_addr_…` recipient and a smallest-unit amount, review the live ACC balance and full transfer details, then consent with the owner passkey. The page uses `PassportAccount.withdrawUnshielded` and reports the confirmed transaction and post-transfer balance. The demo submits these value-moving calls through the loopback funding service, which constructs only the three allowlisted ACC withdrawal circuits with its value-capable wallet; the ordinary sponsor continues to handle other calls. A [fresh node-backed P-256 run](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-p256-unshielded-withdraw-node.json) deposited ten smallest NIGHT units, withdrew four to the public localnet genesis wallet and confirmed the remaining six; the browser route and confirmation UI still need a manual passkey run. The built-in wallet can receive and display an asset but cannot send it from this read-only demo. After indexer sync choose **Refresh wallet balance** to read the recipient balance without a new passkey prompt; the ACC balance is separate.

For scoped unshielded grants, a second browser creates a separate grant-holder passkey and displays its public JubJub key. The ACC owner pastes that key, chooses one asset and one fixed Midnight recipient, and reviews per-call and total caps before `issueGrant`. The demo shows the live grant ID and generation. The owner can unlock the encrypted local journal and export the opening after matching it to the active ACC commitment; the opening JSON must be passed directly to the grantee and is excluded from the shareable log. In the grantee browser, paste that JSON, enter the amount and previous spent total, select the grantee passkey, review the fixed recipient, and call `Spend scoped grant`. The account package checks the live grant, signed challenge, cumulative cap and post-spend commitment. The owner can revoke an active ID and check the inactive tombstone; pending issue recovery remains available. The [node-backed lifecycle](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-p256-grant-holder-node.json) proves issue, independent holder spend, revoke and post-revoke refusal at the package layer. The browser handoff and passkey ceremony remain deferred manual localnet evidence for a later RC.

The local demo can also read sealed shielded holdings after a separate shielded deposit. It compares each opened inbox coin to a successful ACC output event with an exact Merkle index, derives its input nullifier from the current Zswap tree, and excludes it if a successful ACC input event spent that nullifier. The page shows only color, value and inbox index, separately from unshielded balances. Missing or ambiguous chain evidence fails the read. A node-backed P-256 run found the deposited coin, found it again after reopening by address, then excluded it after an exact withdrawal ([evidence](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-p256-shielded-withdraw-node.json)). A two-browser localnet run remains to be recorded. The demo funding button does not create shielded coins.

The second-device demo uses a public JSON handoff. A joining browser creates a passkey and exports only its public reader key, public authoriser key, policy and a fingerprint tied to the ACC/network/binding. The owner browser validates that handoff, shows the live roster and epoch, asks for fingerprint comparison, then calls the SDK's sealed `addDevice` flow. The joiner opens the ACC by address after the owner confirms its commitment on chain. The demo stores openings for grants issued in this browser in an encrypted, passkey-bound local journal; a foreign or lost opening still blocks enrollment with active read grants. The removal control requires the full target commitment and a fresh roster review; the SDK refuses missing readers, holdings or read-grant openings before key rotation. A fresh [node-backed P-256 run](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/experiments/acc-0.35/results/sdk-p256-sealed-device-node.json) confirmed enrollment, both viewing-key openings, key rotation, removal, continued owner access and refusal of the removed passkey. The two-browser UI ceremony still needs a manual passkey run. See the [demo instructions](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/docs/prototype/demo.md#add-a-second-sealed-device).

Keep the funding token, asset policy, reservation file, wallet state, and deployment log outside the repository. The default single-host reservation file is `~/.midnight-passport/funding-reservations.json`. A successful request ID returns its recorded result on replay. An uncertain request stays **pending** and returns HTTP 409 on replay. The funding process journals the initial ACC balance and any returned preparation/deposit transaction IDs before it attempts the next step. Use the read-only [reservation inspector](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/apps/passport-funding-service/README.md) to see those milestones and a stale lock. A durable `noSubmit` marker permits an audited release only when preflight failed before any wallet preparation or deposit. A journaled deposit ID can be reconciled against the localnet indexer's ACC action history only when its successful `deposit_unshielded` action changes the target balance by exactly the reserved amount. The operator command records a verified result for the original request ID. Missing IDs do not prove a transaction was never submitted, and ambiguous cases remain pending. Do not switch to a new UUID merely to bypass a pending result. A stale `.lock` directory also requires inspection before removal. Multiple replicas need a transactional store.

The owner browser stores issued grant openings in a passkey-bound encrypted journal. It has no
backup or cross-profile synchronization, so losing an opening can block later read-grant rotation.
Treat grant recovery as complete only after the chain-backed roster and publication result confirm
it. The full two-browser grant ceremony remains deferred manual localnet evidence for a later RC.

## Audit findings and follow-up

| Area | Reviewed state | Follow-up |
| --- | --- | --- |
| Fund safety | The browser cannot choose an arbitrary amount or target outside the demo deployment log. The funding route enforces asset request/day caps and stores reservations before wallet calls. Completed IDs are idempotent. The localnet operator tool resolves only proved no-submit and exact-credit cases. | A failed or unconfirmed wallet call can still leave an ambiguous reservation pending. Qualify the resolver and transactional storage separately before shared deployments. |
| Confirmation | The backend waits for the ACC balance to increase and returns transaction IDs. The exact-value localnet NIGHT path has node-backed evidence. | Correlate a finalised deposit receipt with the credit for multi-sender deployments; a balance increase alone could come from another concurrent sender. Qualify NIGHT separately on each target network. |
| Secrets and exposure | The browser proxy is localnet/loopback only and keeps the token server-side. The funding route requires a bearer token. | Add authenticated ingress, TLS, rate limits, spending controls, secret management and monitoring for a shared environment. The current demo proxy is not a production API. |
| SDK and deployment | The reusable funding route, typed client and wallet backend are packaged; the NIGHT preparation is in the demo funding application. The published RC5 funding image includes it and passed a mounted-tree localnet NIGHT deposit and same-request replay. | Pin the verified RC5 digest from the release receipt; repeat signed build and mounted-tree checks for future releases. |
| Browser evidence | The UI shows unshielded ACC NIGHT and test-token balances in smallest units. It shows a confirmed deposit and exports the public operation trace. | Add an automated node-backed NIGHT end-to-end test when the CI environment can supply a pinned localnet and proving keys. The current focused test mocks the wallet preparation. |

The audit found no concrete fund-loss issue in the observed localnet path. Its proof is limited to the pinned localnet, the tested ACC and wallet, and the executed checks. Shielded transfers, partial spends, full Lace interoperability, and non-localnet NIGHT funding remain outside this demonstration. See the [problem statement]({{ '/problems/' | relative_url }}) and [release notes]({{ '/release-notes-rc5/' | relative_url }}) for the wider SDK status.
