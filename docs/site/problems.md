## Problem statement

Midnight Passport needs a reusable path from a wallet, browser, or backend to a user's Account Custody Contract (ACC). An integrator needs the same pinned contract binding, proving artefacts, account operations, and service protocol in each environment. The SDK should supply those pieces without requiring every integrator to copy the demo server or own a 12 GB set of prover keys. The ACC is the user's durable account; the service's funded Midnight wallet pays fees and, for a faucet, supplies assets. That wallet is **not** the user's ACC authoriser.

The [target architecture](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/docs/architecture.md), adapted from [upstream PR #29](https://github.com/midnightntwrk/midnight-passport-sdk/pull/29), describes wallet, dApp, and agent entry libraries over an ACC-centred foundation. It is a draft; the fork's [ADR 0007](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/docs/adr/0007-package-set-ports-and-flows.md) is the accepted package boundary for current work. Shared account-owner flows live in `account`, while `core`, `connect`, and `agent` have distinct later roles. The current release implements the foundation and one browser path; the table below states which of the seven integration problems it solves today.

| Problem | Package or application boundary | Current state and next capability |
| --- | --- | --- |
| **1. Distribute the ACC** | `mn-passport-contract` owns the versioned generated binding, circuit catalogue, manifest and integrity loader. `mn-passport-account` consumes the binding through ports. | **Implemented** for `acc-s3r1.1`. Consumers pin the binding and manifest hash; the SDK does not own the upstream Compact source. |
| **2. Distribute proving keys** | `mn-passport-contract` ships ZKIR, small verifier keys, per-file SHA-256 and the `mn-passport-restore-keys` command. A service build restores prover keys into a persistent cache. | **Implemented** as a verified restore path. Prover keys are excluded from npm. A prebuilt cache or object-store mirror may speed deployment, but must verify against the independent package pin. |
| **3. Serve keys for proving** | The standalone [Passport key service image](https://github.com/input-output-hk/midnight-passport-sdk/blob/passport-acc-prototype/apps/passport-key-service/README.md) restores and serves the pinned ACC keys. The future `mn-passport-service` library may reuse its artefact provider. | **Standalone service.** A Node process restores missing prover keys into a persistent volume, verifies the cache before readiness, and streams `/zk/acc/*` with byte ranges. A proof server must pin and check the manifest independently. The demo service still serves its own artefact tree. |
| **4. Sponsor ACC operations** | The service owns its funded Midnight wallet and sponsor policy. `mn-passport-adapter-service` is the client for the `FeeSponsor` and `Submitter` ports; `mn-passport-account` knows only those ports. | **Prototype only.** The standalone `undeployed` localnet has a genesis-funded development seed. Every other network requires `PASSPORT_SPONSOR_SEED`. The current policy pays fees only for eligible calls to registered ACCs; operator deployment needs wallet provisioning and spending controls. |
| **5. Give the browser typed ACC operations** | `mn-passport-account` owns account-owner flows and ports; `mn-passport-contract` owns circuit names and typed binding; `mn-passport-adapter-midnight-js` executes chain calls; `mn-passport-adapter-browser` composes them. Future `connect` serves grant-holding dApps. | **Partial.** Create, open, state and encryption-key rotation are exposed. Add typed helpers for remaining ACC circuits by actor and authorisation rule. A dApp composes and runs its own circuit under a scoped grant; the Passport app does not execute it on the dApp's behalf. |
| **6. Fund an ACC from a Midnight wallet** | A planned faucet handler belongs in `mn-passport-service`; its client belongs in `mn-passport-adapter-service/faucet`. A wallet host can later use the same funding flow without the faucet. | **New requirement; not implemented.** The funded wallet must contribute actual assets to a permissionless ACC deposit. This is separate from paying transaction fees. The current sponsor endpoint refuses transactions that move value. |
| **7. Demonstrate the flows** | `apps/passport-dapp` and `apps/passport-service` compose the published libraries with localnet and the reference wallet. Test and mock helpers remain under `account/testing` and app test code. | **Prototype implemented** for account creation and rotation. Add funding, balance and withdrawal demonstrations after the corresponding APIs exist. The demo apps are private workspace applications, not SDK npm packages. |

`mn-passport-keys` has a narrower meaning than item 2: it contains platform-neutral **ACC secret-derivation recipes**, including the Lace-compatible PRF recipe. It does not distribute `.prover` or `.verifier` files. Keeping the secret source separate from public proving artefacts prevents the package name from implying that prover keys can authorise an ACC.

## Funding is a separate flow

The faucet requirement is a value transfer from an operator-controlled Midnight wallet into an ACC. For an unshielded asset, the flow should select a deployed ACC and asset, construct the binding's `deposit_unshielded` call with the wallet's value input, prove it with the pinned binding, balance and sign with the funding wallet, submit, and confirm the ACC's credited balance. A shielded deposit needs its own typed flow and coin handling. A deposit does not require the recipient's passkey; withdrawing or spending from the ACC does.

The prototype's `/sponsor/balance` deliberately rejects value-bearing offers, so the faucet needs a separate server-side path and policy. Its API must verify the target network and binding, require an explicit asset and amount, constrain who may spend the funding wallet, bound spend per request and over time, make retries idempotent, and report a transaction ID and confirmed balance. The localnet can use its funded default wallet. A non-standalone environment must configure a dedicated funded wallet and deployment policy; the public sponsor route must not become a general wallet-transfer endpoint. `POST /v1/faucet/acc` is a **proposed** route, not an RC1 endpoint.

The upstream contract has `deposit_unshielded` and `deposit_shielded` circuits, but that alone does not prove every asset can be deposited on every network. In particular, the [upstream funding experiment](https://github.com/midnightntwrk/passport/blob/main/contract/evidence/grants-e4-funding-grants-unshielded-funding.json) completed a non-native unshielded deposit while recording a node fee-budget failure for its NIGHT deposit. The faucet must establish supported assets through a node-backed test before advertising them.

## Package rule

Keep the eight implemented libraries in the [package map]({{ '/packages/' | relative_url }}). Add `mn-passport-service` when its reusable handlers and ports are extracted from the demo server. Add subpaths such as `account/circuits` and `adapter-service/faucet` only when their typed APIs and tests exist. Keep `core`, `connect`, and `agent` reserved for the Passport app, dApp grant, and agent entry surfaces in the upstream proposal. Do not release an empty package to represent an unfinished problem.
