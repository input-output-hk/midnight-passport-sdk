# Upstream SDK comparison

**Snapshot: 10 November 2026.** The latest `midnightntwrk/midnight-passport-sdk` main inspected here is [`27721ed`](https://github.com/midnightntwrk/midnight-passport-sdk/tree/27721ed385248e1d40d6353a8ef74a38c94951d4). Its [README](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/README.md) calls it **planning / spec** and says development was reset on 15 October 2026: no SDK package exists there yet. This fork's comparison point is local source [`0293fac`](https://github.com/input-output-hk/midnight-passport-sdk/tree/0293fac13c2b9913c778303bb3d4ae4d56eae7fb), with the separately published [`sdk-v0.1.0-rc9`](https://github.com/input-output-hk/midnight-passport-sdk/releases/tag/sdk-v0.1.0-rc9) release. Thus the table compares **implemented fork behavior with an upstream design**, not two interchangeable releases or a code diff. A fork feature is not automatically an upstream feature.

The [upstream requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md), [package architecture](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/architecture.md), [provider contract](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/provider-integration.md), and [compatibility matrix](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/compatibility.md) define the proposed direction. **Aligned subset** means the fork implements some of the same task with a different or narrower contract. **Divergent** means the present API or trust boundary differs. **Missing** means no equivalent fork feature. These labels are observations, not a roadmap or migration commitment.

| Feature or boundary | This fork today | Difference from upstream design |
| --- | --- | --- |
| Package entry points | **Divergent.** Nine public RC9 packages center on `account`, `protocol`, `keys`, `contract`, adapters, and `service` ([package map](/packages/)). | Upstream proposes `mn-passport-owner`, `mn-passport-connect`, `mn-passport-agent`, `mn-passport-core`, and additional adapters under `@midnight-ntwrk/` ([package architecture](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/architecture.md#packages)). This fork's source `connect` and `core` packages are private scaffolds, not the proposed entry libraries. |
| Account creation and return | **Aligned subset.** `createAccount`, `openAccount`, and optional `openAccountAt` drive a pinned ACC through injected ports ([lifecycle](/guides/account-lifecycle)). | The upstream design puts onboarding and owner authority exclusively in a Passport app; a dApp redirects there and never creates an account or handles device authority ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#onboarding)). This fork lets an integrating host compose account flows, so the host must enforce that separation itself. |
| Passkey/device keys | **Aligned subset.** P-256 and PRF-derived JubJub paths, plus host-owned signer ports, exist ([keys and wallets](/architecture/keys-wallets)). | Upstream specifies one `wa-json134` P-256 profile, key-provider contracts across JubJub/k256/p256, provider-isolated WaaS backup authority, and an owner kernel ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#keys)). This fork does not supply the complete provider matrix or automatically impose the proposed kernel boundary. |
| ACC binding and versions | **Aligned subset.** The `contract` package pins `acc-s3r1.1`, checks artifact identity, and exposes capabilities ([artifacts](/operations/artifacts)). | Upstream plans a version registry and separate wire-protocol and ACC-binding axes; its [matrix has neither axis assigned yet](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/compatibility.md). This fork's API version and single binding are its own compatibility contract. |
| Grants and independent grantees | **Aligned subset.** Bounded grant issuance, use, revocation, and recovery bookkeeping exist for supported ACC calls ([devices and permissions](/guides/devices-grants)). | Upstream proposes browser and agent grant-request profiles, a redirect authorizer, per-origin keys, on-chain grant reads, and calls made while Passport is closed ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#ceremonies)). This fork has no complete `connect` or `agent` entry library and no interoperable ceremony. |
| Proving and sponsorship | **Aligned subset.** Remote service and sponsor adapters plus the reference operator apps exist ([services](/operations/services)). | Upstream's proposed seam is `prove(unprovenTx, circuitIds) → provenTx`; the prover holds or regenerates keys, and the app discloses its witness visibility ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#transaction-in-proof-out)). This fork's current service API and proof-key distribution should not be treated as wire compatible. |
| Fees and payments | **Partial.** The demo uses a fee sponsor and separate funding wallet; the SDK supports ACC deposits and supported withdrawals ([assets](/guides/assets)). | Upstream plans a sponsor or Capacity Exchange path and frames payments to accounts as deposits ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#proving-and-fees)). No Capacity Exchange adapter or universal zero-DUST route is provided here. |
| Private state and device sync | **Partial.** Optional secret-store/durable contracts and demo-local wallet state exist ([durability](/guides/durability)). | Upstream proposes WPP packages, per-dApp package keys, a private-state provider, encrypted storage, handoff, and multi-device sync ([architecture](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/architecture.md#the-owner-kernel-invariant)). These are not delivered as interoperable SDK components here. |
| Total-loss recovery | **Missing.** Existing-device operations and provider-restored passkeys have narrower recovery scope ([lifecycle](/guides/account-lifecycle)). | Upstream specifies guardian/paper-key recovery messages, sessions, successor proof, delay, veto, and viewing-state restore ([architecture](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/architecture.md#recovery)). The presence of recovery circuits in the pinned ACC does not supply this client flow. |
| Naming and identity | **Partial / missing.** Optional checked read-only name resolution exists; DID operations do not ([name port](https://github.com/input-output-hk/midnight-passport-sdk/blob/0293fac13c2b9913c778303bb3d4ae4d56eae7fb/packages/account/src/names.ts)). | Upstream onboarding includes name claim and DID creation ([requirements](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/sdk-requirements.md#onboarding)). Neither is implied by resolving a name. |
| Agents and cross-chain | **Missing.** No public agent SDK or cross-chain call path ([package map](/packages/)). | Upstream plans `mn-passport-agent`, OWS grant keys, transaction joining, and later ecosystem adapters ([architecture](https://github.com/midnightntwrk/midnight-passport-sdk/blob/27721ed385248e1d40d6353a8ef74a38c94951d4/docs/architecture.md#packages)). These future designs have no upstream shipped implementation to compare yet. |

## Integration consequence

Choose this fork's [published package/API contract](/packages/api) and its pinned ACC binding when building against this release. Treat upstream's names, ceremony messages, package layout, and provider rules as design inputs requiring an explicit migration and compatibility review before use. Recheck both repository heads and release tags when this page is updated; neither a planning story nor a passing source test establishes release or network conformance.
