# What remains for 0.2.0?

**Snapshot: 15 November 2026.** The [0.2.0 milestone](https://github.com/input-output-hk/midnight-passport-sdk/milestone/2) has 15 open issues and one closed issue ([#244](https://github.com/input-output-hk/midnight-passport-sdk/issues/244)). An open issue may already have a tested subset; its remaining acceptance is still open. This source branch starts from merged [`passport-acc-prototype` at `1cace66`](https://github.com/input-output-hk/midnight-passport-sdk/tree/1cace66ca395a4ade279714f3dfe6a8b18052267). The published package release remains [`0.1.0-rc9`](https://github.com/input-output-hk/midnight-passport-sdk/releases/tag/sdk-v0.1.0-rc9). Source and localnet results do not silently become release, provider, or public-network qualifications.

The milestone groups candidate work; assigning an issue to it does not mean every Passport v1.0 promise must ship in one SDK release. [Architecture conformance](/architecture/conformance) separates source capability, test evidence, and the broader Passport target.

## Next seven-issue delivery goal

Complete a safe local name-to-ACC journey, then qualify any online route against an independently known mapping and an authenticated, replaceable provider. The connected set is [#334](https://github.com/input-output-hk/midnight-passport-sdk/issues/334), [#315](https://github.com/input-output-hk/midnight-passport-sdk/issues/315), [#247](https://github.com/input-output-hk/midnight-passport-sdk/issues/247), [#316](https://github.com/input-output-hk/midnight-passport-sdk/issues/316), [#317](https://github.com/input-output-hk/midnight-passport-sdk/issues/317), [#318](https://github.com/input-output-hk/midnight-passport-sdk/issues/318), and conformance tracker [#244](https://github.com/input-output-hk/midnight-passport-sdk/issues/244). Start with an explicit failed-original recovery action: only an exact indexed failure plus an absent registry record may release a claim, while the receipt and identifiers remain durable. This source-preview step needs a separate native/browser failure qualification before #334 can close.

The [#244 adoption map](/architecture/adoption-gates) merged in [PR #336](https://github.com/input-output-hk/midnight-passport-sdk/pull/336) and its planning issue closed. Six implementation issues in this connected set remain open.

Qualify the original demo's **post-ACC name claim step** under [#316](https://github.com/input-output-hk/midnight-passport-sdk/issues/316). The source path reuses the opt-in preparation and sponsor fence after the ACC address is known, retains the selected name across reload for the same credential and network, and shows *pending Passport setup* until the original claim and current registry record agree. The fresh browser fixture covers the claim transport and recovery, but not the new panel's complete create/open handoff. Name-owner total-loss recovery, human pre-proof review and the public namespace remain open gates.

The next host integration can expose [#317](https://github.com/input-output-hk/midnight-passport-sdk/issues/317)'s independent sender and [#318](https://github.com/input-output-hk/midnight-passport-sdk/issues/318)'s durable two-leg owner journey as browser journeys beyond the terminal-reviewed local fixtures. Online activation still waits for [#315](https://github.com/input-output-hk/midnight-passport-sdk/issues/315)'s independently known name-to-contract read-only smoke and a supported authenticated provider. The historical Midnight-hosted preprod indexer used by the pinned SDK returns HTTP 410; [current endpoints](https://docs.midnight.network/relnotes/network) require a Blockfrost project token for Preprod/Mainnet and record a 6 November Preview reset. The pinned Preview registry returned no contract through the current v4 indexer on 14 November. No token or unverified online registry mapping is shipped to the browser. Native qualification uses a separately owned stack; neither a documentation build nor a synthetic browser test substitutes for it.
